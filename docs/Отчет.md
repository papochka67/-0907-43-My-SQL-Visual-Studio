# Глава 4. Проектирование базы данных

Схема базы данных проекта ShoeShop была получена из четырёх файлов импорта демонстрационного экзамена, содержавших исходные сведения о каталоге обуви, справочниках и заказах. Первоначально данные были представлены в денормализованном виде: в одной строке одновременно находились наименование товара, его категория, бренд, поставщик, адрес пункта выдачи и статус заказа, а часть ячеек содержала составные значения, например несколько характеристик товара через разделитель. В ходе анализа предметной области повторяющиеся текстовые значения были вынесены в отдельные справочники, а составные ячейки разобраны на атомарные атрибуты, что позволило привести структуру к третьей нормальной форме. В результате вместо исходных плоских файлов была спроектирована реляционная схема из десяти взаимосвязанных таблиц, каждая из которых описывает один объект предметной области и не содержит транзитивных зависимостей неключевых атрибутов.

Структура базы данных зафиксирована в файле db/create_v1.sql, который создаёт базу ShoeShop с кодировкой utf8mb4 и последовательно определяет десять таблиц: categories, manufacturers, suppliers, roles, orderstatus, pvz, users, products, orders и prodorders. Порядок создания выбран с учётом зависимостей: сначала создаются справочники, затем пользователи, товары, заказы и, наконец, строки заказов. Все первичные ключи имеют тип INT с автоинкрементом, что обеспечивает однозначную идентификацию записей и удобство связывания. Для стоимостных показателей применён тип DECIMAL(10,2), поскольку хранение цен в типах с плавающей точкой приводит к ошибкам округления при расчёте итоговой суммы заказа; для хранения дат оформления и выдачи заказа используется тип DATE, а при необходимости фиксации точного времени предусмотрена возможность замены на DATETIME без изменения логики приложения. Строковые поля ограничены разумной длиной (VARCHAR), текстовые описания товаров хранятся в типе TEXT, а поле photo допускает значение NULL, что соответствует товарам без загруженного изображения.

Связи между таблицами реализованы через внешние ключи и отражают бизнес-логику магазина. Таблица users связана с roles по полю role_id, что определяет права доступа пользователя. Таблица products содержит три внешних ключа: category_id ссылается на categories, manufacturer_id — на manufacturers, supplier_id — на suppliers, благодаря чему каждый товар однозначно относится к категории, производителю и поставщику. Таблица orders связана с pvz по полю pvz_id, с users по полю user_id и с orderstatus по полю status_id, что позволяет хранить место выдачи, клиента и текущее состояние заказа. Таблица prodorders связывает заказ и товар: поле order_id ссылается на orders с правилом ON DELETE CASCADE, а поле product_id ссылается на products с правилом ON DELETE NO ACTION. Каскадное удаление выбрано для строк заказа потому, что они являются частью заказа и не имеют смысла при его удалении, тогда как запрет удаления товара при наличии связанных строк защищает историю заказов от разрушения и вынуждает администратора сначала убедиться в отсутствии ссылок.

Для наглядного представления структуры базы данных была построена ER-диаграмма методом Reverse Engineer в MySQL Workbench. Данный метод позволяет автоматически восстановить логическую и физическую модель непосредственно из существующей схемы, что исключает расхождения между документом и фактическим состоянием базы. Диаграмма показывает десять сущностей, их атрибуты с типами данных и связи между ними с указанием кратности; результат экспортирован в файл docs/diagrams/erd.png и включён в отчёт как иллюстрация.

База данных полностью воспроизводима с нуля. Для её развёртывания достаточно выполнить два скрипта: db/create_v1.sql создаёт схему и все таблицы с ограничениями целостности, а db/data.sql наполняет их тестовыми данными, соответствующими подготовленным CSV-файлам из каталога db/import. Дополнительно в составе проекта присутствует файл db/queries.sql, содержащий параметризованные запросы для приложения на C#: авторизацию, выборку каталога, поиск с фильтрацией и сортировкой, получение справочников, добавление, редактирование и удаление товара. Такое разделение обеспечивает прозрачность сопровождения: изменения структуры вносятся в create_v1.sql, тестовые данные — в data.sql, а запросы приложения сосредоточены в одном файле и не дублируются в коде формы.
